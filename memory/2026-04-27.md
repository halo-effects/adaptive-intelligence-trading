## V14PM Paper Bot — Budget Enforcement Fix

**Problem**: Paper PM bot was spending more capital than it had. Cash was -$3,154 with $90K invested against $50K capital. The bot was effectively borrowing money that didn't exist.

**Root Cause (3 layers)**:
1. **Rebalance inflated engine capitals unboundedly**: `_check_and_rebalance` used `eng.capital = max(eng.capital, new_cash)` which only ratcheted UP. 27 engines accumulated $138K in total engine capital against $50K portfolio.
2. **Router allocations based on equity, not cash**: Router computed allocations from `equity * 0.75` ($78K equity → $58K allocations), but didn't check if the sum of all allocations exceeded actual available cash.
3. **Engine capital disconnected from portfolio budget**: Each engine tracked its own `self.capital`, inflated by TP proceeds and rebalance grants. The engine decides to buy based on its own capital, then the runner's bouncer checks the router — but the router's cash counters had also drifted.

**Fix Applied** (run_v14_portfolio_paper.py):
1. **`_compute_portfolio_cash()`** — New ground-truth function: `capital + realized - fees - invested`. Single source of truth for available cash.
2. **Budget-aware rebalance** — Allocations scaled down proportionally if total targets exceed actual portfolio cash. Engine capitals SET (not MAX'd) to `alloc - invested`. Router cash synced to reality after each rebalance.
3. **Hard budget gate in `_process_actions`** — Before any BUY/SHORT_OPEN, verifies portfolio cash can cover the order cost. Belt-and-suspenders on top of router check.
4. **Router reconciliation** — After rebalance, router pool cash synced to `_compute_portfolio_cash()`.

**Key principle**: Engine capitals must never sum to more than the portfolio's actual money. Allocation is a budget, not a suggestion.

**Bot restarted**: PID changes after restart. State restored from engine_state.json. Fix active for budget gate immediately; rebalance fix triggers at next midnight UTC.

**Note**: Live bot (Aster perps) doesn't have this bug because it checks actual exchange balance before placing orders — the exchange itself is the constraint. Paper bot needed software enforcement.

## 2026-05-01: Phase Transition Force-Close Bug (NEAR/USDT -$1,021)

**Problem**: NEAR/USDT on paper PM was force-closed at a -$1,021 loss when the engine detected a "Top fallback" signal and transitioned from LONG_DCA → SHORT_DCA. The engine called `_long_dca_close()` which market-sold all open longs.

**Root cause**: `v14_dca_engine.py` `_check_top_signals()` and `_check_bottom_signals()` called `_long_dca_close()` / `_short_dca_close()` on every phase transition. This directly violated the foundational V14 design principle from `v14-dca-architecture.md`: "Gracefully unwind, let TPs hit."

The wrong behavior was documented in `V14PM_SYSTEM_ARCHITECTURE.md` Section 4.5 ("close all longs, switch to SHORT_DCA"), which contradicted the original architecture doc. The engine was built to the wrong spec.

**Fix (v14_dca_engine.py)**:
- Removed all `_long_dca_close()` calls from `_check_top_signals` (3 paths: OB93+divergence, OB85 fallback, failsafe K50)
- Removed `_short_dca_close()` call from `_check_bottom_signals`
- Phase transitions now change direction only; open positions become orphans

**Fix (v14_lifecycle_engine.py)**:
- Added orphan long TP handling during SHORT_DCA phase (mirrors existing orphan short handling)
- Orphans tick in unwinding mode (TP only, no new layers)

**Documentation updates**:
- `V14PM_SYSTEM_ARCHITECTURE.md` Section 4.5 — corrected all signal actions, added critical rule callout
- `v14-system-spec.md` — added phase transition note
- `tacit/hard-rules.md` — added rules #19 (no force-closes) and #20 (live regime changes need APPROVE)

**Both paper and live bots share the same engine code**, so the fix applies to both. Live bot also had the bug but was additionally protected by its wind-down model (manual APPROVE required for regime changes).

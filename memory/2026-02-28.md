### BOM Bug (state.json)
- PowerShell `Set-Content -Encoding UTF8` writes UTF-8 **with BOM** (EF BB BF)
- Python's json.load() chokes on BOM: `Expecting value: line 1 column 1`
- Bot crashed silently on restart after state.json patch
- **Fix**: Use `[System.IO.File]::WriteAllText($path, $content, [System.Text.UTF8Encoding]::new($false))` — the `$false` means no BOM

### Dedup Key Bug — Deeper Than Expected
- Original dedup key: `symbol+close_time` — too aggressive, blocks legitimate new trades at same candle
- Changed to: `symbol+open_time+close_time` — better but still blocks catch-up trades that replay same cycle
- **Real problem**: On `--skip-backfill` restart, bot catches up on missed candles. Engine executes new trades (closes DCA cycles), incrementing PnL counters. But TradeTracker dedup blocks recording these because they match existing CSV entries from previous restart cycles.
- **Result**: Engine PnL > CSV PnL by ~$2,839 after every restart
- **Fix in progress**: Added `_existing_keys` set populated at load_existing() time. SELL and SHORT_CLOSE in process_actions() now check `_existing_keys` before appending. Prevents re-recording without blocking genuinely new trades.
- Code changes made to `run_v14_paper.py` but NOT yet restarted with fix

### Other Audit Findings
- 5 trades have negative durations (close_time < open_time) — cosmetic, timestamps swapped
- 1 zero-PnL trade (deal #276, LINK) — likely a no-op
- Dashboard trades.csv (docs/data/v14/) still has 377 rows (pre-dedup) — stale
- `deals_completed` now reads from CSV (361) instead of engine counter — correct

### Lessons Learned
- **PowerShell `-Encoding UTF8` adds BOM**: Python can't parse it. Always use `[System.Text.UTF8Encoding]::new($false)` for Python-consumed files.
- **Dedup on save is wrong approach**: Causes silent data loss when legitimate trades match old keys. Dedup at recording time (check before append) is correct.
- **Engine PnL counters and trade log can diverge**: Engine doesn't track individual trades — it just accumulates. Patching one without the other creates inconsistency. Must keep both in sync.
- **`--skip-backfill` catch-up replays trades**: The bot processes missed candles on startup, which can close existing DCA cycles. These are real trades but may duplicate CSV entries from previous runs.
- **Multiple restarts compound the problem**: Each restart → catch-up → engine increments PnL → CSV dedup blocks recording → gap widens.

### Root Cause Found: Wrapper PnL Recalculation Bug
- Wrapper used `pnl_dollar = amount * pnl_pct / (100 + pnl_pct)` instead of engine's actual `pnl` value
- This reverse-engineering formula introduced ~9% rounding/compounding drift across 357 trades
- **Fix**: Added `'pnl': pnl` field to all engine trade records (LONG_DCA_TP, LONG_DCA_CLOSE, SHORT_DCA_TP, SHORT_DCA_CLOSE)
- Wrapper now uses `trade.get('pnl', <fallback formula>)` — exact engine PnL when available, formula fallback for old trades
- After fix + clean backfill: gap dropped from $5,688 → **$124.73** (0.2%, stable)

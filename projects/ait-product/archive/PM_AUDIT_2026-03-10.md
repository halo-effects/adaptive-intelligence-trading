# V14 PM System Audit — 2026-03-10

## Executive Summary

The PM bot has a **fundamental architectural flaw**: it has no engine state persistence.
Every restart creates brand-new engines that process candles as if the bot was just born.
All the "fixes" applied (fresh floor, PID lock, recorded_at, warmup) are band-aids around
this single root cause.

## Root Cause Analysis

### The Core Problem: No State Persistence

The V14LifecycleEngine has `snapshot_state()` and `restore_state()` methods. They exist.
**The PM runner never calls them.** On every restart:

1. `V14PortfolioPaperBot.__init__()` creates a fresh `CapitalRouter`
2. `run()` calls `_check_and_rebalance()` which creates brand-new `V14LifecycleEngine` instances
3. These engines have zero state — no positions, no indicators, no phase history
4. `run_live()` fetches 200 hourly candles per coin from the exchange
5. Each engine processes all 200 candles, generating BUY/SELL actions as it goes
6. TradeTracker records these as completed trades in `trades.csv`

**Result: 8 days of phantom trades generated in seconds.**

### Why `--fresh` Is a Band-Aid

The `--fresh` flag prevents candle replay by:
- Pre-seeding `last_candle_ts` to the latest candle (skips all history)
- Setting `_fresh_floor_ms` as a timestamp floor (catches engines created later by rebalance)

This stops phantom trades but has a massive cost:
- **Engines lose all state** — open positions, phase, indicators, realized PnL
- **Trade history diverges from engine state** — CSV says 22 trades happened, but engines think they just started
- **Equity calculation depends on CSV overrides** — fragile `if csv_realized > total_realized` logic

### Why `--fresh` Keeps Recurring

Without `--fresh`:
- No saved state → engines start from scratch → candle replay → phantom trades
- This happens on EVERY restart: scheduled task, manual start, reboot, crash recovery

With `--fresh`:
- No candle replay, but engines are blind to their history
- TradeTracker loads CSV (correct trade count) but engines have 0 realized PnL
- `_write_status()` patches equity by reading CSV — but only for "realized > engine" direction

### The Dual Instance Problem

The PID lock was added after a scheduled task spawned a second bot. But the PID lock code
was added to the Python file while a pre-lock version was already running. The scheduled task
started the old code (no lock), and both instances wrote to `trades.csv` simultaneously.

## Component-by-Component Findings

### 1. `run_v14_portfolio_paper.py` (PM Runner)

**Critical Issues:**
- **No state save/load**: `snapshot_state()` and `restore_state()` exist on engines but are never called
- **`save_csv()` overwrites the entire file** every cycle from in-memory `self.trades` — if the bot
  restarted with empty trades and hasn't loaded CSV yet, it writes a header-only file
- **Race condition**: `save_csv()` runs every 60 seconds. If the bot starts with empty state,
  it immediately overwrites `trades.csv` with an empty file before `load_existing()` has time to matter
  (Actually: `load_existing()` IS called in `__init__`, but `save_csv()` writes from `self.tracker.trades`,
  which on a fresh engine produces only new phantom trades, wiping the CSV history)

Wait — correction: `load_existing()` is called in `__init__`, BEFORE any candle processing.
So `self.tracker.trades` starts with the CSV data. The issue is that `save_csv()` writes ALL trades
(loaded + new), so phantom trades from candle replay get APPENDED, not replacing. The CSV grows
with phantom trades mixed into real ones.

**Minor Issues:**
- `_compute_current_equity()` uses engine-internal state which resets on restart
- Telegram notifications fire for phantom trades (false alerts)
- No circuit breaker for "generated 20 trades in 5 seconds" anomaly detection

### 2. `v14_lifecycle_engine.py` (Engine Wrapper)

**Issues:**
- Warmup gate added but only affects hourly ticks — **daily boundary ticks still fire and can generate trades**
  even before warmup completes. If a candle crosses midnight, the daily tick runs the full signal stack
  including DCA entries. The warmup then flips True, but a trade may already have been generated.
- `_warmed_up` is not persisted — irrelevant since state isn't persisted either
- `reject_action()` does approximate rollbacks (e.g., `long_layers -= 1`) that may not perfectly
  reverse multi-layer positions

### 3. `v14_capital_manager.py` (Capital Router)

**Issues:**
- Router state is not persisted. On restart, it recreates with full capital, not accounting for
  capital already locked in open positions.
- `return_capital()` adds to `active_pool_cash` without bounds checking — could exceed original pool
  if phantom trades return phantom capital.
- No mismatch detection between router's allocated capital and engines' actual invested amounts.

### 4. `sync_dashboard.ps1`

**Issues (now fixed):**
- `git push --quiet 2>$null` silently swallowed push failures for 17+ hours
- Now has divergence recovery, but the recovery uses `Remove-Item` which requires the script
  not to be `Set-Location`'d into the directory it's deleting

### 5. `trades.csv` (Source of Truth)

**Issues:**
- Used as source of truth for trade history, but has been corrupted 3 times in 2 days
- No schema validation — any CSV with the right columns is accepted
- No integrity checks (e.g., deal_id uniqueness, chronological ordering)
- `recorded_at` field helps detect phantoms after the fact, but doesn't prevent them

## The Correct Fix

### Option A: State Persistence (Recommended)

Add engine state save/restore to the PM runner:

1. On every `_write_status()` cycle, also write `engine_state.json`:
   ```python
   state = {sym: engine.snapshot_state() for sym, engine in self.engines.items()}
   # + router state + tracker open_deals
   ```

2. On startup (without `--fresh`), load `engine_state.json`:
   ```python
   for sym, engine_state in saved_state["engines"].items():
       self.engines[sym] = V14LifecycleEngine(...)
       self.engines[sym].restore_state(engine_state)
       self.engines[sym]._live_mode = True
   ```

3. Engines resume with correct phase, positions, indicators, and `_last_candle_ts`
4. Candle processing picks up from where it left off — no replay, no phantom trades
5. `--fresh` becomes "deliberately start from scratch" instead of "prevent disaster"

### Option B: Strict Fresh-Only (Current Approach, Improved)

If we keep `--fresh` as the default:
1. Accept that every restart loses engine state
2. `trades.csv` is the only continuity
3. Add anomaly detection: if >5 trades are generated within 60 seconds, flag as phantom and discard
4. Add a "recording mode" first 30 minutes after restart — trades generated during this window
   are marked as provisional

Option A is the correct engineering solution. Option B is a hack.

## Recommended Execution Order

1. **Implement state persistence** (`engine_state.json` save/load)
2. **Remove `--fresh` from scheduled task** — no longer needed with state persistence
3. **Add anomaly detection** as a safety net (>5 trades in 60s = phantom)
4. **Add schema validation** to `load_existing()` (reject rows with missing/corrupt fields)
5. **Clean up band-aids**: `_fresh_floor_ms` and the CSV realized PnL override become unnecessary
   with proper state persistence
